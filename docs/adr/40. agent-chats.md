# 40. Agent chats: a chat message is an agent job

Status: Accepted. Amends ADR 29 (chats get a lane of their own; every run takes its folder's model and effort).

## Context

openticker-serve could run the user's coding agent only as an unattended job: a review of one strategy (ADR 29) or a debrief of one day (ADR 39). The user could not talk to that agent from the web app, choose which model or effort it used, see what it did while it worked, or ask a review a follow-up question. To do any of that, they had to leave for a terminal, where the agent had none of the desk's context.

The agent stays the user's own: Claude Code or Codex, signed in as the user, on this machine. OpenTicker never sees a model credential. What was missing was a conversation around the jobs it already ran, and a record of what ran.

## Decision

**A chat is a thread, and each message in it is an agent job.**
- `agent_threads` holds the chat: a title (its first message, cut at 80 characters, or the job's title), its folder, what the folder is about, its harness, the harness's own session id, and the review or debrief it began as.
- Each message is a row in `agent_jobs` of kind `chat`, with its thread, its text, and the model and effort it asked for.
- A message runs as one process of the user's harness, which resumes the thread's session: `claude -p --resume <id>` or `codex exec resume <id>`. Nothing stays running between messages. Each message pays a few seconds of CLI start, and in return there is no process state to lose, reconnect or clean up.
- The message is never on the command line. It goes on the harness's stdin, so nothing reads it as an option and `ps` doesn't show it.

**Two lanes.**
- Background: reviews and debriefs, one at a time, within the day's cap, as before.
- Chat: up to two messages at once, one per thread, with no daily cap. The user is there.

**Folders.**
- A chat lives in one of five folders: General, a strategy, a script, Reviews or Debriefs.
- The folder tells the agent what the chat is about. Claude Code gets it with `--append-system-prompt`. Codex has no system prompt to append to, so the context is its prompt argument and the message, on stdin, is added to it.
- The context carries the job's id. After a restart, that is how the daemon recognises the process as its own.
- A strategy's folder holds its chats and its reviews. The web app's rail shows Recents, then each folder with its count, and opens a folder in place.
- A review or debrief opens its thread in the transaction that queues it. Its first message shows what it was asked. Once it has ended, "continue as chat" is one more message on that thread, which resumes the review's session.

**A chat's key.**
- Each message runs with a key of scope `chat:<thread_id>`, revoked when the message ends.
- The key reaches everything a full key does except broker sign-in, API keys, starting, scheduling or stopping agent jobs and chats (no agent starts agents), and the web app's own routes (`REST_ONLY_ROUTES`). Orders stay paper-only (ADR 11).
- Everything a chat changes is recorded as `chat:<harness>:<thread_id>` and shown as "Claude (chat)" or "Codex (chat)" (ADR 35). Starting and deleting a chat are audited (`AgentChatStarted`, `AgentChatDeleted`).

**What a run uses: one resolve rule.**
- A run's harness, model, effort, spend cap and time limit each come from the most specific level that sets them: the message, the folder's default, the harness Settings picked for every folder, the server's environment (`OPENTICKER_AGENT_*`, now with `OPENTICKER_AGENT_MODEL` and `OPENTICKER_AGENT_EFFORT`), then the harness's own default.
- A level that names the other harness gives only its harness. One harness's model or effort means nothing to the other.
- Effort levels are each harness's own: Claude Code low, medium, high, xhigh and max; Codex minimal, low, medium and high. No model is listed in OpenTicker: both harnesses ship new ones often, and each knows its own and what the user's account may use. Claude Code is asked with an `initialize` control request on its stream-json input, which answers with its /model picker's entries (alias or full name, display name, description, and the full name an alias runs today) without calling a model; Codex with `codex debug models`, keeping what its own picker lists. Each list is kept an hour per CLI version, so an update shows its models at once (`core/agents/catalog.py`). When a harness lists none, any model name is typed.
- A choice the user makes is refused with a reason when the harness can't take it. A stored default that doesn't fit is passed over instead.
- The spend cap is Claude Code's alone.
- Settings › Agents stores the defaults in `agent_settings`: one row per folder kind and one for every folder (harness, runs a day). Its routes are the web app's own.
- Each stored folder choice records the harness its model and effort were chosen for (`chosen_for`). When Settings switch every folder to the other harness, that model and effort are dropped, unless the folder names its own harness.
- The daemon reads Settings on every pass, so a change applies from the next run without a restart.

**What ran is recorded for every run.**
- Every run's stdout is its event stream, kept as `<job>.events.jsonl`: Claude Code with `--output-format stream-json --verbose`, Codex with `exec --json`.
- `core/agents/transcript.py` reads either stream into steps (text, thinking, a tool call with its result, a file edit, an error) and an outcome: session, model, tokens, cost, duration and error. Nothing is stored twice: a thread's steps are read from the file.
- For Claude Code, the model recorded is the one with the most output tokens, because Claude Code also asks a small model for side tasks. Codex reports no model and no cost, so a Codex run records neither.
- Each answer ends with what ran: harness, model, effort, tokens and cost.
- The measure of this decision is the share of ended runs with no model recorded (`agent_jobs_repo.runs_without_model`). It should be 0 for Claude Code runs. Codex runs count against it until Codex reports its model.

**Live steps.** While a message runs, the browser watches its thread over the stream's WebSocket (`watch_thread`). The server reads only the new bytes of the run's event file every 0.25 s and sends the new steps. When the turn ends, the page reads the thread again.

**Edges.**
- Harness not installed: the run ends at once with "Codex is not installed on this machine". The web app offers only an installed harness.
- Session gone: when the harness can't resume the conversation, the thread's session is cleared. The chat can't be continued, and the page offers "Start a new chat with this context", which quotes the last answer.
- Spend cap or time limit reached: the turn ends and says so, in the harness's words or the daemon's.
- Restart: running messages end as `lost`, and their threads stay.
- Delete: a chat leaves the web app. Its messages stay as agent jobs, and its files go with the next prune. A chat can't be deleted while the agent works in it.

## Consequences

- The user talks to their own agent from the web app, in the folder of what it's about, with the model and effort they pick, and sees each step as it happens.
- A review can be questioned once it ends, in the same conversation that wrote it.
- Each message costs a CLI start. A long-lived session (`--input-format stream-json`, `codex app-server`) could come later behind the same port.
- Codex support was built from Codex's documentation and tested on hand-written event fixtures and a fake `codex`. No real Codex run has been made yet. The first one may need fixes.
- A chat's key reaches far more than a review's: the user is in the conversation and asked.
- Jobs from before chats aren't in any thread. They stay on the Connected agents and jobs page with what they printed.
