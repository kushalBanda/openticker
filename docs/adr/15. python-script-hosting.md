# 15. Hosting your own Python strategy scripts

Status: Accepted. Refined by ADR 25 (per-run keys, OPENTICKER_SCRIPT_ID, how memory is limited on macOS).

## Context

Some users already have strategy code. Running it on the platform gives it the same risk checks, audit log and notifications. Hosting it naively is dangerous: handing a child process a copy of the server's environment gives it every secret the server holds, broker keys included.

## Decision

- **Each script runs as its own child process** of the daemon, which starts and stops it, schedules it on chosen weekdays (market holidays skipped), and writes its output to log files under `$OPENTICKER_HOME/scripts/<id>/`.
- **The child environment is built from scratch**, never copied: `PATH`, `HOME`, `LANG`, `PYTHONUNBUFFERED`, `OPENTICKER_URL`, `OPENTICKER_API_KEY`, `OPENTICKER_STRATEGY_ID`. No broker, SMTP, Slack or other secret is passed.
- **Scripts trade only through the REST API**, with an API key scoped to that script. It can place and query orders, read prices and positions; it cannot reach broker login, credentials or strategy administration. The key is revoked when the script is deleted.
- **Memory and CPU time are limited** per script with `setrlimit` (`SCRIPT_MEMORY_LIMIT_MB`, `SCRIPT_CPU_SECONDS`). On platforms without it, scripts are refused rather than run unlimited.

## Consequences

- **Scripts are trusted code.** A script runs as the same OS user as the daemon and could read files that user can read (such as `.env` or the credential key). The clean environment prevents accidental leakage, not a script deliberately looking for secrets. Running code from untrusted authors would need real isolation (a separate OS user or a container) and its own ADR.
- Script hosting works on Linux and macOS only.
