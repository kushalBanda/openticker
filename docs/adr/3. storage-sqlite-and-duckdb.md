# 3. SQLite for transactional state, DuckDB for historical bars

Status: Accepted

## Context

Two differently shaped workloads: small rows written one at a time (credentials, instruments, orders, audit log) and bulk columnar OHLCV history read in ranges.

## Decision

- SQLite (via SQLAlchemy) for transactional state; DuckDB for bars. No abstraction forcing both through one interface.
- Broker tokens are Fernet-encrypted at rest; the key lives at `<OPENTICKER_HOME>/secret.key`, mode 0600. `OPENTICKER_HOME` defaults to `~/.openticker`.
- DuckDB connections are opened per call and closed immediately. DuckDB lets only one process hold a read-write handle on a file, and several OpenTicker processes can run at once (see ADR 2).
- Bars are stored with naive UTC timestamps. `get_bars` takes exchange-local trading dates: Kite stamps a daily candle at 00:00 IST, which is the previous day in UTC. All supported exchanges are Indian, so the exchange timezone is `Asia/Kolkata`.
- Bar writes are all-or-nothing: an invalid batch writes nothing, and a fetch with any failed request returns nothing rather than a partial range.
- No migrations tool yet; tables are created idempotently on connect.

## Consequences

- A non-Indian exchange requires a per-exchange timezone.
- Schema changes to existing tables need a migrations tool before they ship.
