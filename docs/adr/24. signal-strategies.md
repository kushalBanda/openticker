# 24. Signal strategies

Status: Accepted

## Context

Options strategies (ADR 20) enter every leg together, on a start or a schedule. Alert-driven trading works the other way round. A TradingView or ChartInk alert fires one action at a time, on whichever contract the scan picked, whenever it fires. ADR 12 reserved an alert URL for this on `openticker-serve`, authenticated by its own token, and a kill switch that refuses alerts at once. Before this there was no way to act on an alert.

## Decision

We follow openalgo's signal mode, re-derived:

- **A second kind of strategy, `signal`.** Its legs name their contracts outright: a symbol from the instrument master, an exchange and a quantity in units, which must be a whole number of lots. Each leg also sets which alerts it `accepts` (both, long_only or short_only), and its own stop loss, target and trailing stop. The strategy has a `direction` (both, long_only or short_only), an intraday or positional horizon, a schedule and the strategy-wide limits of ADR 19. A leg whose accepted side the direction rules out is refused, and so are shares that could be held short overnight. The kind is fixed: `create_signal_strategy` and `update_signal_strategy` handle signal strategies, and `start_strategy`, `schedule_strategy` and `preview_strategy` refuse them.
- **Four actions**: `long_entry`, `long_exit`, `short_entry`, `short_exit`. Each alert applies one action to one leg:
  - An entry for a position already held that way does nothing.
  - An exit for a position that isn't held does nothing.
  - An entry against a position held the other way closes it first, then enters. If that exit doesn't fill, the entry is not placed.
  - Alert senders repeat themselves, so none of these is an error. There is no dedupe window: long, short, long inside a minute is a real sequence.
- **One run per trading day.** The first entry opens a run, triggered by `webhook`. The run waits for more alerts while flat, and each new position gets its own leg in the run: `leg1`, then `leg1.2`, `leg1.3`. The run ends at `exit_time`, or when the session it opened in has closed with nothing held. The strategy-wide limits, a stop or a kill end it sooner; the next entry then opens a new run. Per-leg stops, stale prices, reconciliation and recovery work as for any run (ADR 21, ADR 23). An entry that fails leaves the run waiting, not stopped. So does one that never reached the sandbox.
- **The schedule is the window**: entries are taken from `entry_time`, on `weekdays`, and nothing is taken from `exit_time`. Exits are taken before `entry_time`, so a position carried in can always be closed. An alert outside the window is recorded as `ignored` and answered 200.
- **One alert URL per strategy**, `POST /webhooks/strategies/{token}` on `openticker-serve`. It sits outside `/api/v1` and needs no API key: the token is the credential, because TradingView and ChartInk can't send a header.
  - `rotate_strategy_webhook` makes a new token and returns it once. Only its SHA-256 is stored, and the old token stops working. The same call names the broker that prices the alerts' orders and sets an optional IP allowlist of addresses or CIDR ranges.
  - `disable_strategy_webhook` removes the URL.
  - uvicorn's access log shows `[token]` in place of the token.
- **Checks, in order:**
  - The token names a signal strategy. If it doesn't, the answer is 404, the same whether the token never existed or was rotated, and the call is not recorded.
  - The strategy has had fewer than 100 calls in the last minute. If it hasn't, the answer is 429, not recorded, so a flood can't fill the table.
  - The kill switch is off. If it isn't, 403.
  - The caller's address is in the allowlist. If it isn't, 403. The address is the one uvicorn reports, which is the `X-Forwarded-For` client only when the proxy is on this machine.
  - The body is a JSON object of at most 16 KB, naming legs and actions the strategy's direction and the leg's `accepts` allow. If it isn't, 400.
- **Two alert formats.** Both go to the same URL:
  - JSON: `{"action": ..., "leg_id": ...}`, or with `symbol` (and `exchange`) instead of `leg_id`. TradingView sends this.
  - ChartInk's payload, recognised by `stocks` and `scan_name`. The scan name carries exactly one of the words BUY, SELL, SHORT or COVER, which map to the four actions. openalgo takes the first word it finds; we refuse a name with none or several. Each stock that is one of the legs becomes a signal. The others are skipped and named in the reply.
- **An accepted alert writes signal commands**, one per signal, which the daemon's runner carries out within a second like any other command (ADR 21). The kill switch cancels any not yet carried out. The runner checks the lock again, and a signal it finds older than 60 seconds is refused. A signal's position is recorded as pending in the same transaction that answers its command. So a daemon that dies mid-entry reconciles the position and never repeats the alert. A later alert for a leg whose entry is still unanswered is refused until it settles.
- **Every call past the rate limit is recorded** in `strategy_signals`: when, from where, the format, the outcome and the commands it wrote. The body is kept only after the token and any key named like a secret are replaced with `[redacted]`, and capped at 2,000 characters. ChartInk echoes the full URL back in `webhook_url`, so this matters. `get_strategy_signals` shows the calls with what the runner did with each.

## Consequences

- An agent can define a signal strategy, hand its URL to TradingView or ChartInk, and leave. Every alert and its outcome can be read back.
- The URL is a bearer credential. Anyone holding it can trade the strategy in the sandbox until it is rotated. The allowlist narrows that when the sender's addresses are known.
- `openticker-serve` must be reachable from the internet for alerts to arrive. The user supplies the tunnel or reverse proxy, and `OPENTICKER_PUBLIC_URL` makes the tools return the full URL.
- The answer to an alert says it was accepted, not what came of it. Fills happen within a second in the runner, and `get_strategy_signals` and `get_strategy_run` show them.
- A signal run ends when it is flat after its session, so a positional position carried overnight stays in yesterday's run until it closes. The daily loss limit counts every run of the day.
