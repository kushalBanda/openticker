# 12. An always-on daemon, with SQLite as its contract

Status: Accepted

## Context

The MCP server runs over stdio and lives only as long as an agent session. Strategies, alerts from ChartInk or TradingView, and resting sandbox orders all have to keep working after the session ends.

## Decision

- **`openticker-serve` is one long-running process** hosting the REST API, alert webhooks, the live price feed, sandbox execution, the strategy runner, the scheduler and the script supervisor. Its loops are threads calling sync use cases (ADR 2); they are inbound adapters like MCP and REST.
- **SQLite is the only contract between the MCP process and the daemon.** MCP tools write strategy definitions and commands (start, stop, kill, close a leg) to a commands table; the daemon applies them within about a second. There is no network call between the two and no shared memory. Either side can restart without the other noticing.
- **A kill switch sets the strategy's lock in the same transaction as the kill command**, so alerts are refused immediately, before the positions are closed.
- If the daemon isn't running, strategy tools still save their changes and say that the daemon needs starting.
- **REST requires an API key** (stored hashed) on every route except alert webhooks, which authenticate with their own token. It binds to `127.0.0.1` unless `OPENTICKER_BIND` says otherwise.
- **Broker sessions expire daily.** The daemon checks the session before trading. On expiry it pauses new entries on every strategy, notifies, and resumes once `connect_broker` stores a fresh token.

## Consequences

- Start, stop and kill take effect up to about a second after the tool returns.
- Exposing alert webhooks to the internet is the user's choice (a tunnel or reverse proxy set in `OPENTICKER_PUBLIC_URL`); nothing is public by default.
- Unattended strategies still need a daily broker login.
