# 2. Synchronous use cases; SQLite always via NullPool

Status: Accepted

## Context

OpenTicker is self-hosted and single-user. Both MCP and FastAPI can call sync functions (FastAPI runs sync routes in a thread pool). Still, concurrent access is real: overlapping tool calls run on separate threads, and several OpenTicker processes (one MCP server per agent session, a REST daemon) can open the same SQLite file at once.

## Decision

- `core/` and `use_cases/` are synchronous. No async coloring.
- `storage/sqlite/engine.get_engine()` always builds its engine with `NullPool`: a fresh connection per use, never a shared one. `StaticPool`'s single connection gets its cursor state corrupted under concurrent use (`bad parameter or other API misuse`).

## Consequences

- Simple call stacks, easy testing, no event-loop concerns in the domain.
- Revisit only if a genuinely concurrent multi-user scenario appears.
