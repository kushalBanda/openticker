# 1. Hexagonal architecture with Protocol ports and one broker registry

Status: Accepted

## Context

OpenTicker is driven from several entry points (an MCP server for agents, later a REST API and screener webhooks) and talks to several outside systems (brokers, notification channels, storage). Domain rules (order validation, risk checks, options math) must not depend on any of them.

## Decision

- Ports and adapters. `core/` holds pure domain logic with no I/O and no framework imports. `ports/` holds the interfaces `core/` and `use_cases/` depend on. `adapters/` implements them. Dependencies point inward only.
- Ports are `typing.Protocol`s, not ABCs. Adapters satisfy them structurally, with no inheritance. An adapter must implement the whole Protocol; methods not built yet raise `NotImplementedError`.
- One use case is one plain function, taking its adapters as arguments. Use cases call storage modules directly; there is no repository interface layer on top.
- `core/` and `ports/` use frozen dataclasses. Pydantic or plain dicts appear only at the inbound edge.
- `adapters/brokers/registry.py` is the only place a broker name maps to an adapter (and to a login-URL builder). Inbound adapters never special-case a broker by name.

## Consequences

- A new inbound adapter reuses every use case unchanged; a new broker is one adapter plus one registry line.
- Protocols catch an incomplete adapter only at type-check or call time, not at class definition. Acceptable at a handful of brokers.
- Registration is explicit (grep finds every broker), at the cost of remembering to register a new one.
