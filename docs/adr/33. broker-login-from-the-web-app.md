# 33. Broker login from the web app

Status: Accepted. Amends ADR 5, which stays how an agent connects.

## Context

ADR 5 has the human copy a `request_token` out of the broker's redirect and hand it to an agent, because nothing listened for the redirect. `openticker-serve` now listens on this machine and serves a signed-in web app (ADR 30, ADR 31), so the redirect can land on it. Kite logs everyone out daily, so this is a daily step and worth one click. Two things stand in the way: the browser session's cookie is `SameSite=Strict`, which a browser leaves off any navigation that arrives from another site, the broker's redirect included; and a stored session must never be exchanged for someone else's login.

## Decision

- **The callback.** `GET /brokers/{broker}/callback?request_token=…&status=…` on `openticker-serve`. The user registers `http://127.0.0.1:8750/brokers/zerodha/callback` as their Kite app's redirect URL; Settings shows the exact URL with a copy button. A successful login calls `connect_broker` (stored encrypted, ADR 5), publishes `BrokerConnected` with `triggered_by` `ui`, and redirects to `/settings?connected=<broker>`; a cancelled login or a broker error redirects to `/settings?connect_error=<why>`. Settings reads the flag once, says it in a toast and clears it.
- **Only a signed-in browser's login is kept.** The callback requires the session cookie (ADR 31). Because the cookie is `SameSite=Strict`, the first answer to a request without it is a small page of ours that opens the same URL again with `bounced=1`: that navigation starts on this server's own page, so the browser sends the cookie. A request still without a session after the bounce gets a page saying to sign in first; the token is not used. The cookie stays `Strict`.
- **Fallback.** When the redirect URL points elsewhere (the Kite app is shared with another tool), Settings takes the pasted `request_token` and calls `POST /api/v1/brokers/connect`, the same route an agent's REST client uses.
- **Disconnect.** `DELETE /api/v1/brokers/{broker}/session` deletes the stored session and publishes `BrokerDisconnected`. `GET /api/v1/brokers/{broker}/session` says whether one is stored, whether it is live, when it expires, the last recorded login and whether the broker's app keys are set: never the token. A Kite login is stored as expiring at the next 06:00 IST, when Kite logs every session out, so the page says "Session expired" from then on instead of "Connected".
- **The feed follows at once.** `openticker-serve` reopens the live feed on `BrokerConnected` or `BrokerDisconnected` for that broker instead of waiting out its one-minute retry. A feed that finds no session stored (`BrokerNotConnectedError`) logs it and publishes nothing: `BrokerSessionExpired` is for a session the broker refused, not for one the user never made or removed. A login made in another process (stdio MCP) still reaches the feed on its next retry.
- `connect_broker` takes the event bus and who asked, over MCP (`mcp:<client>`, ADR 35), REST and the web app alike.

## Consequences

- Reconnecting each morning is: Settings (or the expired-session banner), Log in to Kite, log in, back on Settings, connected.
- A login redirected to a browser that isn't signed in costs one extra login after signing in: the request token is single-use and short-lived, so nothing is kept for later.
- The redirect URL names `127.0.0.1` and the port; serving on another port means registering that URL instead.
