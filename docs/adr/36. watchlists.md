# 36. Watchlists

Status: Accepted. Builds on ADR 8 (tool design), ADR 17 (every tool has a route), ADR 32 (the stream tails the audit log) and ADR 35 (who did it).

## Context

A user watches more instruments than they hold. Until now the only way to stream an instrument that wasn't a position or a pending order was the `OPENTICKER_WATCH` environment variable: one list, set before the server starts, invisible to agents. The web app needs named lists the user keeps and changes from the page, and an agent should read and change the same lists ("add the NIFTY banks to my Banks list"), so the page and the agent never disagree.

## Decision

- **Stored on the server, shared by everyone.** Two SQLite tables: `watchlists` (id `wl_…`, name unique, position, created_at) and `watchlist_items` (watchlist, exchange, symbol, position). Lists keep the order they were made in; instruments the order they were added in. There is no reordering yet.
- **Six MCP tools, each with its REST route**: `list_watchlists`, `create_watchlist`, `rename_watchlist`, `delete_watchlist`, `add_to_watchlist`, `remove_from_watchlist`. Only a full key reaches them; a script's or a review's key doesn't (ADR 25, ADR 29).
- **Bounded.** At most 20 lists and 50 instruments on a list, so a list is one `get_quotes` call. A name is 1 to 40 characters and unique whatever its case ("Banks" and "banks" aren't two lists).
- **Checked on the way in, not on the way out.** Adding an instrument checks it against the instrument master (an unknown one is refused, nothing added). Adding one already on the list leaves it where it is. Removing one not on the list is ignored, and removing isn't checked against the master, so a list never gets stuck with an instrument it can't lose.
- **Each change is an event.** `WatchlistChanged` (created, renamed, deleted, added, removed, with the symbols) is published only when something changed, and says who did it (`triggered_by`, ADR 35). The audit log records it, so the web app's stream hears of an agent's change and refetches the lists: the page updates within about a second, from whichever process made the change. It is a record: listed in Activity, never a toast or a bell item.
- **A list doesn't stream by itself.** The feed streams what a page subscribes to (ADR 32), so a list is priced live while the Watchlist page shows it; its bid, ask, day's range and volume come from polling `get_quotes` every 2 seconds, as the stream carries only the last price. `OPENTICKER_WATCH` still streams what it names.
- **The paper-account reset (ADR 37) leaves watchlists alone**: they aren't part of the account.

## Consequences

- An agent can build and read the user's lists as it does anything else, and the user sees it happen.
- The web app remembers which list it showed last in the browser only; the lists themselves are the server's.
- Reordering, and a list streaming while no page shows it, would each need another decision.
