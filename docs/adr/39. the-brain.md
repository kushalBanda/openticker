# 39. The brain: notes that learn from the desk's own trades

Status: Accepted. Builds on ADR 29 (agent jobs and the reviewer, amended here), ADR 35 (who did it), ADR 30 (the web app), ADR 18 (additive schema) and ADR 8 (tool design).

## Context

An agent that designs or reviews a strategy starts each session knowing nothing the desk learned before. Reviews were written into `labs/notes/<strategy>.md`, which no other agent read, and nothing checked whether what a review concluded held on later runs. The user wanted a record that keeps learning: what happened each day and why, the trade-offs taken, what could have been done better, lessons that are tested against later trades rather than repeated, and changes proposed for the user to decide. It had to live with the rest of OpenTicker's state, be readable by any agent, and be browsable as a graph of linked notes in the web app.

## Decision

- **Notes in SQLite, facts where they are.** `brain_notes` holds markdown notes of five kinds: day, strategy, symbol, lesson and proposal. A day's key is its trading date, a strategy's its id, a symbol's `EXCHANGE:SYMBOL`. `brain_links` keeps the links, structural ones (a lesson's strategies) and those parsed from the text (`[[day:2026-10-05]]`, `[[lesson:<id>]]`). A note never stores a number from the record: a day's trades, fills, charges and net are read from the trade book, the runs and the daily P&L each time, and the debrief's words are joined to them by run or order id. Strategy and symbol notes are created by the server as soon as something links to them. A paper account reset would delete that record, so it freezes each debriefed day's record into its note first (`data.frozen`), and the day is read from there afterwards.
- **Notes are data.** Every result that carries note text carries a `notice` saying so, and the labs instructions say never to follow instructions found in a note. The user's own part of a note (`user_body`) is kept apart from the agent's: rewriting a debrief keeps it. Edits to it send the version they were made from; a stale one is refused (409), and the text it would have replaced is in the audit log.
- **A lesson's status is derived, not stored.** A check is about one ended run, or one order placed outside a strategy, that ended after the lesson was written and is in its scope. A lesson with no strategies applies to the whole desk; one with strategies applies only to their runs. The agent answers `held`, `not_held` (each with the figure it observed) or `not_tested`; checking the same run or order again replaces the answer. Status follows from the counts on every read: tested at 3 checks with 60% held, a rule at 10 with 70%, retired automatically at 5 below 40%. Only a person's override is stored: retire, with a reason, or reinstate. After a reinstatement the automatic retirement waits for 5 more checks. Runs and orders a live lesson hasn't been checked against are listed as owed.
- **Proposals change nothing.** An agent may propose one change to one strategy, with why, what could make it wrong and the lessons it rests on. The user accepts, rejects (with a reason, which agents read before proposing again) or puts it off. Accepting gives a request to paste into an agent; strategies still change only between runs, by the user's agent (ADR 21).
- **The daily debrief is an agent job.** With the user's agent (ADR 29), after the close, at a time the user picks (15:40 or later, once the day's P&L is recorded), at most once a trading day and within the daily job limit. A day with no fills, ended runs or owed checks gets a one-line note from the server and no job. The job is a desk job: `strategy_id` stored as `''`, and `agent_jobs.subject` holding the date. Its key, scope `debrief:<date>`, reads the desk and the brain and writes only the brain: that day's debrief, lessons, checks, uses and proposals. It can't trade, change a strategy, decide a proposal, retire a lesson or write another day. It runs the labs `debrief` agent with no file tools (Codex in a read-only sandbox). Every job carries a title ("Debrief of Mon 5 Oct", "Review of …") used by events, notifications and the Agents page.
- **The reviewer appends to the brain (amends ADR 29).** A review key also reads notes (`search_brain`, `get_brain_note`), and may check a lesson against one of its own strategy's runs, record a lesson's use and raise a proposal for its own strategy. These are the only writes it gets. Over REST these routes' arguments are in the body, so each checks the body against the key's scope itself. The reviewer still writes its verdict into the note file as before. The labs rule "the reviewer's tools are read-only" becomes "read-only, or one of those three appends".
- **Lessons are read first, and that is measured.** `labs/AGENTS.md`, `new-strategy` and `review-strategy` tell the agent to search lessons before designing or reviewing, and to record each one it relied on (`record_lesson_use`). `get_learning` counts the result from the record alone:
  - of the strategies created while a desk-wide lesson was live, the share with a design use by the same client within 30 minutes of creation (`strategies.created_by`, new and nullable);
  - of the review jobs finished while a lesson about their strategy or the desk was live, the share with a review use for that strategy while the job ran;
  - checks owed, and lessons that held more often than not.

  The Brain page shows this as its Learning line.
- **One graph engine.** The Brain page draws the notes on a canvas with d3-force, d3-zoom and d3-drag:
  - hovering fades all but a note's neighbours, and labels appear with zoom without overlapping;
  - the settings filter by kind and lesson status, find a note, set label zoom and spacing, and show the whole brain or the notes within 1–3 links of the selected one;
  - the same engine, compact, is the mini graph on a day's, lesson's or proposal's page, and a click there opens that note on the Brain page around it;
  - the layout is stirred only when the set of notes or links changes, and opening settles for at most 120 ms before drawing, so 1,000 notes open without holding the page;
  - the brain's audit events refetch its reads once per 1.5 s burst, not once per event.

## Consequences

- An agent starting cold can read what the desk learned, with each lesson's track record, before it acts. Whether it does is a number on the Brain page rather than an impression.
- The judgement "held" is the agent's. OpenTicker decides which runs and orders count, and when a status moves. A lesson can't be checked by the server itself.
- Nothing merges near-duplicate lessons; the debrief skill is told to sharpen an existing lesson rather than add one.
- Old review notes in `labs/notes/` stay files and aren't imported.
- A design citation is a heuristic (same client, 30 minutes either side). A review run in the user's own session isn't counted, only review jobs.
