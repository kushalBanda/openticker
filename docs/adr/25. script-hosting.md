# 25. Running hosted scripts

Status: Accepted. Refines ADR 15.

## Context

ADR 15 decided that users' own Python strategy scripts run as child processes of the daemon, with an environment built from scratch, a REST key scoped to trading, and memory and CPU limits. Building it settled the parts ADR 15 left open: how the MCP server reaches processes only the daemon owns, what happens to scripts when the daemon stops or crashes, how a schedule behaves, and how memory can be limited on macOS, which refuses `setrlimit` for memory.

## Decision

We follow openalgo's script host where it is sound, re-derived:

- **Starting and stopping are commands.** `start_script` and `stop_script` write rows to `script_commands`, the same contract as strategies (ADR 12, ADR 21); the daemon's script supervisor carries them out within a second. Scripts are uploaded as source text (at most 256 KB) that must parse as Python; parsing runs none of it. The source is `$OPENTICKER_HOME/scripts/<id>/main.py`, and that folder is the script's working directory and its `HOME`. A running script, or one about to start, can't be changed or deleted.
- **A key per run, not per script.** Each run gets a fresh API key with scope `script:<id>`, named `script-<run id>`, created as it starts and revoked as it ends. The key lives only in the child's environment and as a hash, so no plaintext key is ever stored for the daemon to hand over later. On start the daemon revokes every script key but those of runs it is still watching. A script key reaches quotes, market depth, the broker's margin for orders, bars, option chains, instrument search, market status, risk checks, and placing (one or a basket), listing, changing and cancelling orders, one order's status, today's trades, positions and funds, and closing one position. Anything else answers 403: broker login, strategies, scripts, the audit log, cancelling every order or closing every position. Its orders are audited as `script:<id>`. Key names starting `script-` are reserved.
- **The environment is exactly** `PATH` and `LANG` (copied), `HOME`, `PYTHONUNBUFFERED`, `OPENTICKER_URL`, `OPENTICKER_API_KEY` and `OPENTICKER_SCRIPT_ID`, which replaces ADR 15's `OPENTICKER_STRATEGY_ID` because a script is not a strategy. macOS adds `__CF_USER_TEXT_ENCODING` to every process. `OPENTICKER_URL` is the daemon's own bind, with a wildcard bind reached through loopback. The script runs under the daemon's Python, so the packages OpenTicker installs, `httpx` among them, are available.
- **Limits.**
  - CPU time: `RLIMIT_CPU` set in the child before the script starts (`SCRIPT_CPU_SECONDS`, default 3600). The system ends a script that uses it up with SIGXCPU: reason `cpu_limit`.
  - Memory: measured every second for the script's whole process group and killed with SIGKILL, not asked to stop, once over `SCRIPT_MEMORY_LIMIT_MB` (default 1024): reason `memory_limit`. On macOS the measure is the physical footprint, compressed pages included. Under memory pressure a process's resident size can be a few MB while it holds hundreds. On Linux it is the resident size. The run's peak is written to `peak_memory_kb` whenever it rises by 1 MB or more (`PEAK_MEMORY_STEP_KB`), so the once-a-second measurement doesn't turn into a write every second; the web app shows it against the limit (slice 12).
  - Output: a run that prints more than 50 MB is stopped: `log_limit`.
  - Hosts that aren't Linux or macOS refuse to start scripts rather than run them unlimited.
- **Stopping** sends SIGTERM to the process group, so anything the script started stops too, and SIGKILL after 5 seconds. Positions the script opened are left as they are.
- **How a run ended** is recorded on the run and in its log: `exited`, `failed` (a non-zero code or a signal we didn't send), `stopped`, `schedule`, `memory_limit`, `cpu_limit`, `log_limit`, `daemon_stopped`, `lost`, `start_failed`. Each start and end is notified. The last 10 runs' logs are kept.
- **A schedule runs a script once a trading day.** It has a start time, an optional stop time, weekdays (Monday to Sunday), and the exchange whose holidays and special sessions count. From the start time, on a scheduled day that exchange trades, the daemon starts the script if it isn't running and hasn't had that day's run. The day's run is any run since today's start time that ended for a reason other than the daemon's absence. So a script that exits early or is stopped by hand stays stopped until the next day, and one ended by a daemon restart is started again while the window is open. Unlike a strategy's entry (ADR 22), a late start is allowed: the script decides whether to trade. The stop time stops any run past it, however it was started.
- **When the daemon stops** (SIGTERM or Ctrl-C), it stops every script and records `daemon_stopped`. uvicorn raises SIGTERM again after its own shutdown. The daemon handles that signal by exiting through its shutdown path; the default handler would have ended the process first.
- **When the daemon comes back**, a script still running under the recorded pid, checked against its command line, is watched again; its exit code is then unknown. A run whose process is gone ends `lost`. If it had been started by hand it is started again, as openalgo does; a scheduled one is left to its schedule. A process running the script that no run recorded (a crash between starting it and saving its pid) is killed.

## Consequences

- An agent can upload a script, run it now or on a schedule, read its output, and stop it, all without the script ever seeing a broker key.
- Scripts are still trusted code, as ADR 15 says: they run as the daemon's user.
- A script started by hand is started again after a crash, from the beginning. One that places an order when it starts places it again. Scripts should read their positions before acting.
- Memory is checked once a second, so a script can briefly go past its limit before it is killed.
- Orders from scripts pass the same sandbox checks, capital cap, audit log and notifications as any REST order.
