# 31. Browser sign-in and sessions

Status: Accepted.

## Context

Every REST route needs an API key (ADR 17). A browser can't be handed one safely: a key in page script can be read by any script on the page, and pasting a key into a form is a poor first minute. The server listens on this machine only, but that alone doesn't stop another site: a page the user visits can send requests to 127.0.0.1, and a page can rebind its own domain name to 127.0.0.1 (DNS rebinding).

## Decision

**A one-time link, swapped for a cookie** (as Jupyter does).
- `openticker-serve` prints `http://127.0.0.1:8750/login?token=…` when it starts, and opens it in this machine's browser once the server answers (not with `--no-browser`, nor when stdout is not a terminal, so a service or test never opens one); `openticker-serve ui login` prints a new one from another terminal. A link works once, for 10 minutes. Only its SHA-256 is stored (`ui_sign_in_links`), as for API keys: 32 random bytes are far too many to guess from a hash.
- Opening it creates a session (`ui_sessions`, again only the hash) and sets `ot_session`: HttpOnly, SameSite=Strict, Path=/. A used, expired or unknown link gets a page saying how to get a new one, and no cookie.
- A session lasts 30 days from its last use. Using it pushes the expiry on, written at most once a minute; the app renews the cookie each time it loads, and an open tab's stream renews the session every minute. Sign out ends this browser's session; sign out everywhere ends all of them. There is no second check before dangerous actions: those use hold-to-confirm buttons instead.
- A session is also a visit log for the Today view: use after 10 idle minutes starts a new visit, and when the browser was last here before it is kept (ADR 34).

**Where a cookie is accepted.** With no `X-API-Key`, the cookie is tried:
- only when the `Host` header is a loopback name on this server's port, so a rebinding page, which arrives under its own name, is refused;
- for a request that changes something (anything but GET, HEAD, OPTIONS) and for the stream's WebSocket, only when `Origin` is this server's own origin under any loopback name, or the Vite dev origin with `--dev`;
- a refused cookie is a 403, a missing or ended session a 401 that says how to sign in.
A browser session has the full scope. What it does is recorded as done by `ui` (`triggered_by`). An API key still works exactly as before and wins when both are sent. MCP over HTTP (`/mcp`) takes keys only.

## Consequences

- The first minute is: start the server; the web app opens, signed in.
- Anyone with a shell on this machine can sign in, by design: they can already read `~/.openticker`.
- Binding to a non-loopback address still serves the app, but the cookie is never accepted there; such a setup needs API keys.
