# 10. Domain events, audit log and notifications

Status: Accepted

## Context

When an agent places an order or a risk rule fires, several things must follow: a durable record of what happened and who caused it, and a message to the user on the channels they chose. If every use case called storage and each notification channel directly, adding a channel would mean editing every use case, and a slow or failing channel could stall or break a trade.

## Decision

- **Use cases publish events** (`events/types.py`: `OrderPlaced`, `OrderFailed`, `RiskBreached`, `InstrumentSyncCompleted`), frozen dataclasses with a tz-aware UTC `occurred_at`. They depend only on `EventPublisher.publish` and know nothing about subscribers.
- **`EventBus`** (`events/bus.py`) is in-process publish/subscribe. A subscriber is either:
  - **inline**: runs in the publisher's thread before `publish` returns. Used for the audit log, so the record is on disk before the tool responds and survives the process exiting straight after;
  - **background**: runs on a small thread pool. Used for notifications, so network calls never delay the caller.
- **The background queue is bounded** (`max_pending`, default 1000). At the cap, the next handler runs inline in the publisher's thread: nothing is dropped and memory can't grow without bound. An unbounded queue is a known way for a long-running trading process to run out of memory.
- **A failing handler is logged and isolated**: it never raises into the publisher or stops other handlers.
- Subscribing to a class receives instances of it and its subclasses; subscribing to `object` receives every event.
- **Audit log**: every event is written to the append-only SQLite `audit_log` table (type, time, `triggered_by`, fields as JSON). Agents read it with the `get_audit_log` tool.
- **Notifications**: `OrderPlaced`, `OrderFailed` and `RiskBreached` are sent to every configured channel. `NotificationPort.send(subject, message)`; where a message goes is the adapter's configuration. Channels:
  - **Slack** via an Incoming Webhook (`SLACK_WEBHOOK_URL`): no bot token or OAuth app.
  - **Email via SMTP** (`SMTP_*`, `NOTIFY_EMAIL_*`): one stdlib adapter covers any provider, since Resend, Amazon SES, Gmail and others all offer SMTP. Port 465 uses implicit TLS, others STARTTLS.
  - One channel failing does not stop the others.
- **Configuration is read in one place**, `composition.py`, which builds the bus from environment variables. No channel configured is valid (events are still audited). Partial SMTP settings fail at startup rather than at the first order.
- On shutdown the MCP server closes the bus, waiting for queued notifications.

## Consequences

- A new channel is one adapter plus one line in `composition.py`; use cases don't change.
- Background notifications still queued when the process is killed (not shut down) are lost. The audit log is not affected, since it's written inline.
- Delivery is best effort, with no retries. A failed notification is logged, not retried.
- WhatsApp and Telegram are out of scope; either would be another `NotificationPort` adapter.
