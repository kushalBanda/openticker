# 30. The web app and how it is served

Status: Accepted.

## Context

Agents operate OpenTicker through MCP. People still need to watch what the agents did and step in: close a position, stop a strategy, see today's P&L. The REST API (ADR 17) can do all of it, but not at a glance. The user runs `openticker-serve` on their own laptop, so a second server, a second port or a Node runtime at install time would each be one more thing to start and keep running.

## Decision

**One process, one port.** `openticker-serve` serves the web app at `/`, next to the REST API at `/api/v1`, MCP at `/mcp` and the alert URLs at `/webhooks`, on 127.0.0.1:8750.
- The app is a React single-page app. Its source is `ui/`; `pnpm build` writes it to `src/openticker/adapters/inbound/web/dist/`, which is gitignored and shipped inside the wheel and the sdist. A hatch build hook builds it when pnpm is there. Users never need Node.
- `adapters/inbound/web/` is its inbound adapter: sign-in (ADR 31), the live stream (ADR 32) and serving the files. `create_app` mounts it only when given the stream hub and the web settings, so tests and tools that want the REST API alone get exactly that.
- Files under `/assets/` have hashed names and are cached for a year. Every other GET that no route claims gets `index.html`, uncached, so the app's own routes (`/positions`, `/strategies/…`) load on refresh. Paths under `/api/`, `/mcp`, `/webhooks/`, `/login`, `/brokers/` and `/health` never get the page: a wrong API path stays a JSON 404. A new non-API route must be registered before the catch-all.
- A source checkout that was never built serves a plain "the web app isn't built" page with the command that builds it (503). The REST API and MCP work regardless.
- The app calls the same REST routes an API key does. There is no separate backend for the browser.

**Each page is its own chunk**, fetched when first opened; once the first page shows, the rest are fetched while the browser is idle, so moving between pages never waits on the network. Charts and the code viewer load with the first page that needs them. The JavaScript a first visit needs stays under 350 KB gzipped (about 206 KB at launch).

**A page says what didn't load, where it would have been.** A request the server refused (4xx: not there, not allowed) isn't asked again; a server or network fault is, twice. Then the tile, table or stat that needed it reads "Positions didn't load: <why>. Try again", or "—" for a single figure: never a 0, an empty list or a "none" the server didn't say. An older figure stays while a refetch fails.

**Every route is held to the same bar by the e2e suite**, not only each page's own spec: no sideways scroll at 1280, 1440 and 1920 in both themes; axe finds no WCAG 2.1 A or AA fault in either theme, the order window, palette and bell included; with reduced motion nothing moves; each page with the server failing, the market closed, no broker, and the broker's session expired; and 60 frames a second while prices tick on each live screen.

**Development** runs Vite on :5173, which proxies `/api` (the WebSocket too), `/login` and `/brokers` to `openticker-serve --dev`. `--dev` accepts that origin (ADR 31) and prints sign-in links that open through Vite. `pnpm gen:api` writes the app's API types from FastAPI's OpenAPI; CI fails when they drift.

## Consequences

- Installing OpenTicker installs the web app; opening it is one link.
- Frontend changes need Node 22 and pnpm, for contributors only.
- The catch-all makes a mistyped app route show the app's own "not found" page instead of a server 404.
