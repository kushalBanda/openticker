# 35. Who did it: the source of an order, and who holds a position

Status: Accepted. Positions and their close dialog use it now; orders, trades and the activity feed show it as their pages are built.

## Context

Many hands trade the one paper account: the user in the web app, Claude Code or Codex over MCP, strategies, TradingView alerts, hosted scripts, REST clients, and the server itself (square-off, expiry settlement). Every order and audit entry already records `triggered_by`, but only as the entry point: every MCP client was the same `"mcp"`. The web app has to say who did each thing, and a position can be part a strategy's and part the user's: the sandbox keeps one net position per contract and product.

## Decision

**MCP calls carry the client's name.** The name a client gives in its `initialize` handshake (`clientInfo.name`) is normalised (lower case, spaces as hyphens: "Claude Code" is `claude-code`) and recorded as `triggered_by = "mcp:<name>"`. A client that gives none is still `"mcp"`. `ScopedMCPServer.call_tool` puts the name in a context variable for the call (sync tools run in a thread, which copies it), and the tools read it instead of writing `"mcp"`. Names are labels the client chose, never an identity: nothing is allowed or refused by them.

**Clients are noted** in `agent_clients` (name and transport, `stdio` or `http`, with version, first and last seen, and a call count), written at most once a minute per client with the calls in between counted. The Agents page and the first-run checklist read it.

**`source` is derived, never stored.** `core/pnl.source_of(triggered_by)` reads a record as one of: `you` (`ui`), `claude-code`, `codex`, `agent` (any other client, plain `mcp`, a review job), `strategy`, `alert` (`webhook`), `script`, `schedule`, `rest`, `system` (anything else, and none). Orders, trades and audit entries return it beside `triggered_by`. Old rows are not rewritten: plain `mcp` reads as an agent.

**Positions say who holds them** (`use_cases/position_holders.py`). Each running strategy's open legs on the contract are counted, per strategy, on the run's product; what is left of the net quantity is the rest, labelled by who placed the newest non-strategy fill that added to the position (a buy for a long, a sell for a short). When the legs don't fit inside the position (opposite sides, or more than it holds), it is marked `shared` and has no rest. `held_by` and `shared` are on every position, over MCP and REST alike.

**Closing** from the web app offers what the holders allow: the strategy's legs (a close-leg command its runner carries out; the default when a strategy holds part), the whole position (one market order; strategies keep running and find their legs flat, as `close_position` already does), or stopping the strategy. A shared position defaults to closing all of it.

## Consequences

- The web app can write "Claude", "NIFTY futures trend" or "You" on every row without a schema change beyond `agent_clients`.
- The rest's label is a best reading of the order history, not a ledger: if both the user and Claude added to one position, it says whoever added last.
- A client can call itself anything; the label is only as good as its handshake.
