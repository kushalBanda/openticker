# 18. Additive schema changes without a migrations tool

Status: Accepted

## Context

OpenTicker keeps its state in a SQLite file that survives upgrades. Tables are created with SQLAlchemy's `create_all`, which adds missing tables but never changes existing ones. Resting orders needed new columns on `sandbox_orders`, and an existing database would have failed on its first read.

A migrations tool (Alembic) adds a dependency, a versions directory and a step for every schema change. Almost every change so far has added something: a table, or a column.

## Decision

- **On first use in a process, `get_engine()` creates missing tables and adds missing columns** to existing ones with `ALTER TABLE ... ADD COLUMN`. It does all of this in one transaction holding SQLite's write lock, because the MCP server and the daemon can start together and each must see the other's changes before deciding what is missing.
- **Only nullable columns can be added this way.** Code reads a missing value (NULL) as the column's default: `triggered` as false, `reserved_margin` as 0. A new column that isn't nullable fails loudly at startup, naming itself, rather than being added wrong.
- **Anything else is a real migration.** Renaming, dropping, retyping or tightening a column needs a migrations tool, which gets adopted the first time one is needed.

## Consequences

- Upgrading is just installing the new version. No command to run, and no version table.
- New columns are nullable even when every new row sets them; readers treat NULL as the default.
- Removed columns stay in old databases, unused.
