# CLAUDE.md — packages/strategy

This file gives guidance for work inside `packages/strategy`. Read the root `/CLAUDE.md` first for workspace-wide rules.

## What this package does

`strategy` is the bar-by-bar backtest engine, with pluggable strategies loaded via a registry. It depends on `ingest` (for `Bar` data) and `quant` (for signals/sizing). This engine is hand-built on purpose, see "Explicit constraints" in the root `/CLAUDE.md` — do not replace it with an off-the-shelf backtesting library.

## Commands

Run these from the repo root, not from inside `packages/strategy`.

- Run all tests for this package: `uv run pytest packages/strategy/tests`
- Run a single test: `uv run pytest packages/strategy/tests/core/test_engine.py::test_name`
- Type check: `uv run mypy packages/strategy`
- Lint: `uv run ruff check packages/strategy`

## Architecture

- `core/engine.py`'s `BacktestEngine.run()` drives the bar loop: for each bar, it calls `strategy.on_bar(bar, portfolio, broker)`, then matches any pending orders against the *next* bar's data (`broker.match_pending_orders`), applies fills to the `Portfolio`, then marks the portfolio to market on the current bar. Orders placed on bar `i` fill on bar `i+1`, never same-bar — do not change this ordering without understanding it introduces lookahead bias.
- `core/interfaces.py` defines the `Strategy` and `Broker` protocols. `core/models.py` defines `Order` and related trade types shared with `execution` (execution imports `strategy.core.models.Order` and `strategy.core.portfolio.Portfolio` directly).
- `core/portfolio.py`'s `Portfolio` tracks positions, cash, average cost basis per symbol, and mark-to-market P&L across the backtest run. It owns a `TradeLedger` (`core/ledger.py`) internally, exposed read-only via `Portfolio.ledger` — every fill applied through `apply_fills` also produces a `LedgerEntry` (side, quantity, fill price, commission, cost basis before the fill, realized P&L, cash/position after). Realized P&L uses average-cost accounting via one unified signed-delta formula (buy = +quantity, sell = -quantity), not separate long/short branches — see `docs/superpowers/specs/2026-09-03-trade-ledger-design.md` for the full derivation including the flip-through-zero case. `apply_fills` raises `ValueError` on any `Order.side` other than buy/sell rather than silently no-op'ing.
- `storage/ledger_store.py`'s `LedgerStore` persists a `Portfolio.ledger`'s entries to the same shared DuckDB file `ingest`/`quant` use, in the `ledger_entries` table, keyed by a caller-supplied `run_id` (not generated internally) plus a `sequence` column for fill order. Written once, in a batch, after a backtest run finishes — never per-fill inside the hot loop.
- `storage/equity_curve_store.py`'s `EquityCurveStore` persists a `Portfolio.equity_curve` (the daily mark-to-market series, one point per bar) in the `equity_curve_points` table, same run_id/sequence keying and write-once-after-run pattern as `LedgerStore`. This is a distinct series from the ledger: the ledger only has points on bars where a trade actually filled (irregular spacing), the equity curve has a point on every bar (regular spacing). Anything that needs roughly evenly spaced observations — `quant.features.statistics.sharpe_ratio`'s annualization-factor bucketing, in particular — must read from this store, not derive a curve from ledger fill timestamps (a sparsely-trading strategy's fill gaps can land outside every annualization bucket and raise `InsufficientDataError`).
- `core/registry.py` holds the name-to-class registry for strategies, same self-registration pattern as `ingest`/`quant`. Strategies register with `@register_strategy("name")`, build instances through `StrategyFactory` rather than importing classes directly.
- `backtest/broker.py` is the in-memory `Broker` implementation used for backtesting. `execution/brokers/paper/broker.py` is a separate, promoted implementation for paper trading — the two are not the same class, keep backtest-only concerns out of `backtest/broker.py` if they belong in the paper broker instead (and vice versa).
- `core/trigger.py` and `core/action.py` split a strategy's entry/exit logic ("when") from its order-generation logic ("what"). A `Trigger.check(symbol, bars) -> bool` answers whether a condition fired on this bar; it carries no order-side logic and, deliberately, no portfolio access — a condition that needs to know the current position (e.g. a direction-dependent exit) does not fit this protocol and is read directly in the strategy instead (see `mean_reversion`'s `_check_exit`). An `Action.execute(symbol, bar, portfolio, broker) -> None` turns a fired trigger into an order; it carries no timing logic. Built-in triggers: `CrossoverTrigger` (fires once on the bar a fast signal crosses a slow signal in a given direction, tracks each symbol's baseline internally), `ThresholdTrigger` (fires while a signal's value is above/below a level, no edge detection), `BollingerRsiEntryTrigger` (fires when price closes outside a Bollinger band with RSI confirming the extreme — reads `quant.features.technicals` directly rather than through a `Signal`, since Bollinger bands are inherently 3 values (lower/middle/upper) and don't fit `Signal.compute`'s single-scalar return). Built-in actions: `EnterLongAction` (buys unless already in position), `ExitLongAction`/`ExitShortAction` (close the full long/short position unless already flat that way), `ReverseToLongAction`/`ReverseToShortAction` (size an order to flip straight from short to long or long to short in one fill, no-op if already at the target position). This is now the standard shape for a new strategy's in/out logic — see `strategies/sma_cross/strategy.py` for the reference composition. When a strategy needs both an entry trigger and an exit trigger driven by the same underlying relation (as `sma_cross` does), check both every bar rather than short-circuiting with `elif`, each trigger keeps its own internal baseline and goes stale if skipped.
- `strategies/<name>/strategy.py` holds one strategy per subpackage (e.g. `sma_cross/`, `buy_and_hold/`, `mean_reversion/`). Each self-registers, and should compose `Trigger`/`Action` instances in `__init__` rather than inlining entry/exit conditions and order construction directly in `on_bar` — not every strategy needs a `Trigger`, though: `buy_and_hold` has no timing condition at all, it composes `EnterLongAction` alone (idempotent by design, no extra "already bought" flag needed); `mean_reversion`'s exit condition is read inline for the portfolio-access reason above. A strategy's own bar-history buffer must be sized to the longest lookback any of its triggers/exit logic needs (`mean_reversion` sizes its `deque` to `max(bb_window, rsi_period + 1)`, not just `bb_window` — a buffer capped too short silently starves a trigger of the one bar it needs and it never fires). Strategies are ported from `docs/resources/backtesting.py` and `docs/resources/nautilus_trader` reference implementations where possible, formula/logic matched rather than reinvented — `sma_cross` ports backtesting.py's `SmaCross`, `buy_and_hold` follows the standard QuantStart/event-driven-backtester `BuyAndHoldStrategy` shape (buy every symbol once on its first bar, never exit) — the standard baseline to compare an active strategy's return against — `mean_reversion` ports nautilus_trader's `BBMeanReversion` (`examples/live/architect_ax/strategies.py`): Bollinger Band mean reversion with RSI confirmation, flips straight through an opposite position on entry, exits back to the middle band. Note nautilus's own RSI indicator is 0..1 scale; `quant.features.technicals.relative_strength_index` is 0..100, thresholds are not interchangeable between the two.
- No standalone strategy-run config file (`config/strategies.yaml` was removed) — a strategy run's name + params are supplied by the caller at call time: the server API's `BacktestRequest` body (`packages/server/src/server/schemas/backtest.py`, a pydantic discriminated union on `strategy_name` — one request model per strategy, e.g. `SmaCrossRequest`, `BuyAndHoldRequest`), or a script's `--strategy`/`--param key=value` CLI flags (see `scripts/run_live_backtest.py`, `scripts/run_live_paper.py`). `StrategyFactory.create(name, params)` is the single entry point either caller goes through.
- `metrics/performance.py` computes backtest performance metrics off a finished `Portfolio`.

## Adding a new strategy

1. Create `strategies/<name>/strategy.py`, implement the `Strategy` protocol from `core/interfaces.py`.
2. Build its entry/exit logic from `Trigger` implementations (`core/trigger.py`) and its order logic from `Action` implementations (`core/action.py`). Add a new `Trigger`/`Action` subclass there first if the strategy needs a condition or order pattern that does not exist yet, rather than inlining it in the strategy.
3. Decorate the class with `@register_strategy("<name>")`.
4. No config file entry needed — params are passed in by the caller (server request body or script `--param` flags) at run time.
