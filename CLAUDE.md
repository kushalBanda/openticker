# CLAUDE.md

Guidance for Claude Code (and other coding agents) working in this repository. Maintainers may also have a gitignored `CLAUDE.local.md` with private workflow notes.

## What this repo is

**OpenTicker**: a self-hosted, agent-operated trading platform for Indian markets. An MCP client (Claude Code, Codex, ...) operates it directly through tool calls: connect a broker, sync instruments, search symbols, fetch quotes, historical bars and option chains with Greeks, and paper trade in a local sandbox, where fills pay the bid or ask and Indian charges (ADR 28). The same operations are served over a REST API with API keys (`openticker-serve`, ADR 17), which also streams live prices from the broker. A market calendar keeps orders to open sessions. Sandbox orders can be changed while they wait, placed as a basket (buys first), and cancelled or closed all at once; quotes come in batches of up to 50 with bid, ask and five levels of depth, and the broker's own margin for a set of orders, hedge benefit included, is one call away (ADR 26). Risk rules, an audit log and notifications are built. Options strategies can be defined and previewed (ADR 20), then started by hand or on a schedule (ADR 22): that server enters them in the sandbox and watches them unattended (ADR 21), falls back to quotes when the feed goes quiet, stops a run whose prices are lost, and reconciles runs after a restart (ADR 23). Signal strategies are driven by TradingView or ChartInk alerts posted to a per-strategy URL on that server (ADR 24). Users' own Python scripts run under that server too, each with a clean environment, a per-run API key scoped to trading, and memory and CPU limits (ADR 15, ADR 25). Users do their research from the `labs/` folder, which sets up Claude Code and Codex with shared instructions and skills (ADR 27), including a read-only reviewer that judges a strategy's ledger after costs and writes its verdict into the strategy's note (ADR 29). That server can run the reviewer unattended as an agent job, when asked or on the user's schedule for that strategy (every so often, after so many runs, or on a drawdown), with the user's own Claude Code or Codex and a key that reads only that strategy, and serves MCP over HTTP at `/mcp` for it (ADR 29). A web app (`ui/`, served by `openticker-serve` at `/`, ADR 30) shows all of it: browsers sign in with a one-time link printed by the server (ADR 31) and get live prices over one WebSocket (ADR 32); each page loads on first use, and one that can't load its data says what didn't load and why, never a 0 or an empty list the server didn't give (ADR 30). Every order, trade and audit entry says who did it (you, Claude, Codex, a strategy, an alert, a script), MCP clients recorded by name, every order the strategy or script that placed it by name, and every position which running strategies hold part of it (ADR 35). The web app's order window shows the margin the paper account itself would block (`preview_paper_margin`, ADR 26). Every paper fill keeps its charges item by item and the P&L it realized, and the trade book covers today, this week or this month (ADR 28). `list_strategies` says what each strategy is doing now (running, listening, scheduled with its next entry, stopped, killed), with today's and all-time net after costs and its latest review's verdict; the web app's strategy page adds its legs marked live, its equity curve after costs and its alert URL (ADR 29). The web app hears of everything as it happens, whichever process did it: the stream tails the audit log every half second (ADR 32), toasts fills and stops, raises a banner when a strategy is killed or the broker session expires, counts what hasn't been read in a bell, and its Activity page filters the log by kind and by who (ADR 35). `openticker-serve` records the paper account's P&L each minute of the session and each day after the close, which `get_pnl_history` and `get_charges_summary` read; the web app's Dashboard opens on today's P&L after charges, its minute line and what happened since the browser's last visit, and walks a new user through connecting a broker, syncing, adding an agent and a first paper order (ADR 34). Each instrument has a page (`/symbols/<exchange>/<symbol>`): its quote, candles with the user's paper fills marked and moved by live ticks, market depth, and its orders today. Named watchlists live on the server, read and changed by agents (six tools) and the web app's Watchlist page alike, each change audited as `WatchlistChanged` so the page shows an agent's change as it happens (ADR 36). The Option chain page shows one expiry live with bids and asks and the nearest futures; picked bids and asks make a basket whose payoff at expiry and today (`preview_payoff`, also a tool), margin with hedge benefit and charges show before it places as paper orders, buys first (ADR 38). Its Scripts page starts, stops and schedules a hosted script and follows its log live as it runs, with each run's peak memory against the limit; its Agents page lists the MCP clients seen with their calls today and stops a waiting or running review job (ADR 25, ADR 29). Its Settings page logs in to the broker through the broker's own redirect to that server, or a pasted token, and logs out (ADR 33); shows the instrument list, the paper account's settings and charge rates; creates API keys, shown once, and revokes them; and resets the paper account, a full wipe refused while a strategy or script runs (ADR 37). Its Brain page shows what the desk learned as a graph of linked notes: days, lessons and proposals beside the strategies and symbols they're about (ADR 39). An agent job debriefs each trading day after the close if the user turns it on: why each run and hand-placed order was traded, what was given up, what could have been done better, and whether each lesson owed a check held. A lesson's status (hunch, tested, rule, retired) follows from those checks. A proposal changes nothing until the user decides it. The labs skills read lessons before designing or reviewing and record which they relied on, and the page's Learning line counts how often they did.

Design decisions and their reasoning live in `docs/adr/` (`1. hexagonal-architecture.md` onward). Read the relevant ADR before changing an area; add a new ADR when making a decision a future contributor would otherwise have to reverse-engineer.

## Core stack

**Python 3.13, `src/` layout, `uv`.** `uv sync` installs everything. Entry points: `openticker-mcp` (MCP over stdio, spawned per agent session, no port) and `openticker-serve` (long-running REST server, plus `keys create|list|revoke`).

Key libraries: `mcp` (the SDK is 2.x: `FastMCP` was renamed `MCPServer`, import from `mcp.server.mcpserver`, not the `fastmcp` path most examples online show), `pydantic` (result models at the MCP and REST edges only), `fastapi` + `uvicorn` (REST), `sqlalchemy` (SQLite), `duckdb` (bars), `httpx` (sync client), `cryptography` (Fernet, credentials encrypted at rest), `python-dotenv`.

## Architecture (hexagonal, ADR 1)

```
core/         domain logic. Zero I/O, zero framework imports. orders/ (order shapes, validation, sandbox fill and margin math, resting-order matching, fill prices and charges and the check against the broker's, ADR 28), risk/ (position risk rules, strategy-wide rules over several legs), options/ (Black-76 Greeks, chains, ADR 16), calendar/ (trading days and session hours, ADR 13), strategies/ (strategy definitions and leg resolution, ADR 20; runs, their legs and ratchets, ADR 21; schedule.py, when entries and exits are due, ADR 22; prices.py, when a leg's price needs polling or is stale, ADR 23; signals.py, reading alerts and what each does to a leg, ADR 24; ledger.py, a strategy's runs and totals after costs, ADR 29), scripts/ (hosted scripts' schedules, limits and why a run ended, ADR 25), agents/ (agent jobs' settings, why one ended, the review and debrief prompts and job titles; reviews.py, when a scheduled review is due, ADR 29; debriefs.py, when the daily debrief is due, ADR 39), brain/ (notes.py: note kinds, keys and wikilinks; lessons.py: checks and a lesson's derived status; proposals.py; learning.py: whether lessons are being read, ADR 39); web.py (browser sign-in rules, ADR 31); pnl.py (`source_of`: who did it, from `triggered_by`, ADR 35; a day's figures after charges, ADR 34).
ports/        Protocol interfaces, shared DTOs (models.py), shared errors (errors.py). script_process_port.py: the child processes scripts run in; agent_job_port.py: the ones agent jobs run in.
adapters/     implementations: brokers/ (registry + zerodha/, including the WebSocket feed), sandbox/ (paper trading, ADR 11), notifications/ (slack, email), scripts/ (supervisor.py: starts scripts with a clean environment and limits, ADR 25), agents/ (harness.py: runs `claude -p` or `codex exec` for a job, ADR 29), inbound/ (web/: the web app's sign-in, stream and static serving, ADR 30–32; mcp_server.py, mcp_models.py, rest_api.py, scopes.py: what each key reaches, for REST and MCP alike, mcp_scoped.py: MCP over HTTP at /mcp, daemon/: main.py entry point, feed_loop.py, execution_loop.py, strategy_loop.py, script_loop.py, agent_loop.py, charge_check_loop.py, pnl_loop.py (the P&L record, ADR 34), quote_poller.py, prices.py).
use_cases/    one flat function per operation, not a class. May call storage directly; publish events. strategies/ groups the strategy operations: define.py (definitions), control.py (commands, alert URLs), runner.py (the daemon's side, ADR 21; scheduled starts, ADR 22; reconciling orders with the sandbox, ADR 23; signal entries and exits, ADR 24), signals.py (alerts arriving at a strategy's URL, ADR 24), ledger.py (the one read a review needs, ADR 29), board.py (every strategy's state and money, for `list_strategies`, ADR 29). scripts/ groups the hosted-script operations: manage.py (what MCP and REST call), supervise.py (the daemon's side, ADR 25). agents/ does the same for agent jobs (ADR 29). brain/ is the brain (ADR 39): read.py (the graph, search, a note with its links, a day's record joined from the trade book, learning), write.py (debriefs, lessons, checks, uses, proposals, the user's note), debrief.py (asking for and scheduling the daily debrief).
events/       EventBus, event types, subscribers (audit_log inline, notifications background), ADR 10.
composition.py  builds the event bus, notification channels and the sandbox (`order_broker`) from env. The only place they're wired.
storage/      sqlite/ (transactional state), duckdb/ (bars), ADR 3; script_files.py (scripts' source and run logs under `$OPENTICKER_HOME/scripts/`); calendar_file.py (shipped `data/holidays.json`, overridable at `$OPENTICKER_HOME/holidays.json`).
```

Dependencies point inward: `adapters -> ports <- use_cases -> core`. Nothing in `core/` or `ports/` imports from `adapters/` or `use_cases/`.

- **`Protocol`, not `ABC`, for every port** (ADR 1).
- **One broker registry**: `adapters/brokers/registry.py` maps broker names to adapter builders and login-URL builders. Inbound adapters never special-case a broker name; they call `get_adapter()` / `get_login_url()`.
- **Frozen dataclasses in `core/` and `ports/`.** Pydantic exists only at the inbound edge: `mcp_models.py` (shared by MCP and REST) and request bodies in `rest_api.py`.
- **Sync, not async, throughout `core/` and `use_cases/`**, and SQLite always via `NullPool` (ADR 2). Don't "fix" either.
- **A `BrokerPort` implementation must satisfy the full Protocol**: methods not wired yet raise `NotImplementedError("<what> is not implemented yet")`.
- **Broker errors derive from `ports.errors.BrokerError`** with messages that say how to recover. The MCP edge turns agent-fixable errors into `ToolError`; anything else stays an opaque crash (ADR 7).
- **Every MCP tool has a REST route** returning the same result model (ADR 17); `test_every_mcp_tool_has_a_rest_route` enforces it. REST maps the same agent-fixable errors to 404/502/503. What a key reaches is one table, `adapters/inbound/scopes.py`, for REST and for MCP over HTTP (`/mcp`, ADR 29): a hosted script's key (scope `script:<id>`) reaches only prices, orders and positions (ADR 25); a review job's key (`review:<strategy_id>`) reads only that strategy, market data and the brain's notes, and may append to the brain about that strategy only (a lesson check on its runs, a lesson's use, a proposal: their REST routes check the body with `refuse_outside_scope`); a debrief job's key (`debrief:<date>`) reads the desk and writes only the brain, that day's debrief included (ADR 39). A new tool needs its route in `TOOL_ROUTES`; a stdio call (no HTTP request) is the user's own session. The one route without an API key is a signal strategy's alert URL (`/webhooks/strategies/{token}`, ADR 24): its token is the credential, stored only as a hash and never logged.
- **MCP tools follow ADR 8**: title, annotations, every parameter described, Pydantic result model, bounded responses. `test_every_tool_is_fully_described_for_agents` fails any tool that doesn't. A tool that changes something records `triggered_by=_who()` ("mcp:<client>", ADR 35), never a literal "mcp".
- **Times**: stored and passed around as tz-aware UTC; returned to agents exchange-local (`+05:30`). Input dates are exchange-local trading dates (ADR 3).
- **Importing a module must be side-effect-free.** `load_dotenv()` runs only in the entry points' `main()` (`mcp_server`, `daemon/main`).
- **Risk rules are pure functions** in `core/risk/` (ADR 9 per position, ADR 19 per strategy): absent prices are `None`/0 and never defaulted, direction is `side` never a signed quantity, stop loss beats target.
- **Side effects go through events** (ADR 10): use cases publish, subscribers audit and notify. Never call a notification channel from a use case.
- **Anything time-dependent takes the clock as a parameter** (`now`, or a `clock` callable at the edges: `mcp_server.clock`, `create_app(clock=...)`). Tests pin it to a trading time; nothing reads the wall clock deep inside.
- **Live prices come through `MarketFeedPort`** (ADR 13). `ticks()` raises `BrokerSessionError` when the broker refuses the session; `FeedLoop` turns that into one `BrokerSessionExpired` event. Never log the Kite ticker URL: it carries the access token.
- **Schema changes are additive** (ADR 18): a new column on an existing table must be nullable, and readers treat NULL as its default. `get_engine()` adds it to old databases. Anything else needs a real migration.
- **Strategy control is a command** (ADR 12, ADR 21): MCP, REST and alerts (ADR 24) write `strategy_commands` rows; only the daemon's runner places strategy orders, recording each in `strategy_orders` before sending it. A running strategy is never edited or deleted. Scripts work the same way (`script_commands`, ADR 25): only the daemon starts or stops their processes.
- **A script's environment is built from nothing** (ADR 15, ADR 25): never `os.environ.copy()`. Only `PATH` and `LANG` are copied; broker, SMTP and Slack settings must never reach a script. An agent job's is built the same way (ADR 29): what the harness needs to find the user's sign-in, and the job's key, which never goes on the command line.
- **Order placement is sandbox-only** (ADR 6, ADR 11): `SandboxBroker` wraps the real broker adapter for prices; broker adapters' order methods raise `NotImplementedError`. Sandbox fills go through `sandbox_repo.fill_transaction()` (`BEGIN IMMEDIATE`). Every fill pays the book and the charges in `data/charges.json` (ADR 28), which the daemon checks daily against the broker's contract note (`BrokerPort.get_charges`, never called during a fill); tests not about costs use `tests/fixtures/sandbox.py`'s frictionless settings. Resting orders are filled by the daemon through `SandboxPort` (`use_cases/execute_resting_orders.py`); intraday square-off is `use_cases/square_off.py`; expiry settlement is `use_cases/settle_expired.py` (price rules in `core/orders/settlement.py`).
- **`labs/` is for users, not contributors** (ADR 27). Each skill exists twice, `labs/.claude/skills/<name>/` and `labs/.agents/skills/<name>/`, identical; `tests/test_labs.py` fails if they drift. `labs/CLAUDE.md` is only `@AGENTS.md`. The reviewer agent exists for each too (`.claude/agents/reviewer.md`, `.codex/agents/reviewer.toml`), with the same OpenTicker tools, each read-only or one of the brain's three appends (ADR 39); `tests/test_labs.py` fails if either gains another. So does the debrief agent (`.claude/agents/debrief.md`, `.codex/agents/debrief.toml`): the brain's tools and the desk's reads, no file tools.
- **Code comments reference ADRs, never internal planning docs.** This repo is public.

## Commands

- Install: `uv sync`
- Tests: `uv run pytest`
- Type check (must pass clean, strict): `uv run mypy src tests`
- Lint: `uv run ruff check src tests`
- Run the MCP server: `uv run openticker-mcp`
- Run the REST server: `uv run openticker-serve` (create a key first: `uv run openticker-serve keys create <name>`); it prints a sign-in link for the web app and opens it in the browser (not with `--no-browser` or without a terminal), `uv run openticker-serve ui login` prints another
- Web app (`ui/`, Node 22 + pnpm): `pnpm install`, `pnpm build` (into `adapters/inbound/web/dist/`), `pnpm dev` against `openticker-serve --dev`, `pnpm check`, `pnpm typecheck`, `pnpm test`, `pnpm e2e` (fake broker, `tests/fixtures/e2e_server.py`; every route is checked for sideways scroll, axe, reduced motion, failure and no-broker states and 60 fps), `README_SCREENS=1 pnpm e2e --project=app readme` retakes the README's screenshots, `pnpm gen:api` after changing a route

## Tests

`tests/` mirrors `src/openticker/`. `tests/conftest.py` gives every test its own `OPENTICKER_HOME`, so nothing touches `~/.openticker`. `tests/fixtures/fake_broker.py` (`FakeBrokerPort`) is a network-free broker; MCP tool tests register it under the name `"fake"` and exercise the full tool -> registry -> use case -> storage path. HTTP in adapter tests is faked by monkeypatching `httpx`.

## Secrets

`.env` (gitignored) holds broker API credentials. Never print or commit its values. Broker session tokens are stored Fernet-encrypted and never returned by any tool (ADR 5).
